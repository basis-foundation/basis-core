## 1. Scope of the Review

This review covers, as merged on `main` at commit `dcfc739`:

- the v0.1 compatibility surface (domain, decisions, policy, audit, enforcement, adapters, as documented in `docs/public-api.md`'s stable and extension tiers);
- the additive operation-aware surface (shared vocabulary, evidence references, request/context models, the structured policy data model, trace/evidence artifacts, `OperationAwareDecisionResponse`, and the operation-aware enforcement boundary);
- deterministic policy evaluation, including condition semantics and the ten-operator registry;
- response, trace, and audit-evidence assembly;
- the operation-aware enforcement point (`OperationAwareEnforcementPoint`);
- public API exports (`__all__` per package versus `docs/public-api.md`);
- canonical conformance (the five canonical scenarios against the vendored `basis-schemas` snapshot);
- import boundaries (`tests/test_import_boundaries.py` and related targeted recursive guards);
- governance (`docs/breaking-change-discipline.md`, `docs/schema-versioning.md`, and the rest of the governance document set);
- documentation completeness;
- test and quality gates (pytest, ruff, mypy, `git diff --check`);
- release metadata readiness (version files, changelog/release-notes scope).

This review does **not** cover, and does not treat as blocking for this library's release unless the repository's own release criteria say otherwise: `basis-gateway` implementation (including `GatewayAuditEvent` production, persistence, or enforcement); deployment packaging; external IdP integration; protocol adapter implementations (`basis-adapters`); production performance certification or benchmarking; an external, third-party security audit; or the act of publishing the release itself (tagging, packaging, PyPI upload). `basis-core`'s own Definition of Done (Section 16 of the roadmap plan) does not make any of those external concerns a gating condition for this library's v0.2.0 readiness, and this review does not invent one.

### Deterministic evaluation

The implemented path covers every stage named in the brief: policy validation (`policy/operation_aware/validation.py`), applicability (`policy/operation_aware/applicability.py`), selector matching (`policy/operation_aware/selector.py`), condition evaluation (`policy/operation_aware/condition_eval.py`, `operators.py`), effect aggregation with deny precedence and default deny (`policy/operation_aware/aggregation.py`), `NOT_APPLICABLE` handling, trace assembly (`evaluation/operation_aware/trace_assembly.py`), response and audit-evidence assembly (`evaluation/operation_aware/response_assembly.py`), and operation-aware enforcement (`enforcement/operation_aware.py`, `OperationAwareEnforcementPoint`). Orchestration in `evaluation/operation_aware/engine.py` (`OperationAwareEvaluationEngine`) sequences these policy-owned stages without reimplementing their semantics, per ADR-0006 and `docs/import-boundaries.md`. Each module is covered by its own dedicated test file under `tests/operation_aware/` (`test_policy_validation.py`, `test_applicability.py`, `test_selector.py`, `test_condition_eval.py`, `test_operators.py`, `test_policy_aggregation.py`, `test_trace_assembly.py`, `test_response_assembly.py`, `test_evaluation_engine.py`, `test_operation_aware_enforcement_point.py`), all passing (Section 7).

### Condition semantics

The architecture clarification this plan's Section 8 gated on is approved and present in the locally available `basis-architecture` checkout (`docs/architecture/condition-operator-semantics.md`). The condition registry is implemented, not deferred: `SUPPORTED_OPERATORS` in `src/basis_core/policy/operation_aware/operators.py` is a fixed, ten-member `frozenset[str]` (`equals`, `not_equals`, `in`, `not_in`, `greater_than`, `greater_than_or_equal`, `less_than`, `less_than_or_equal`, `exists`, `not_exists`), confirmed by direct inspection of the module and matching `docs/operation-aware-evaluation-semantics.md` Section 4's table exactly. Confirmed behaviors, from the same module and `docs/operation-aware-evaluation-semantics.md`:

- **No silent coercion** — every comparison operator classifies both operands into a family (`string`/`number`/`boolean`/`array`/`timestamp`/`structured_object`) and requires a family match before comparing; a mismatch is always `error`, never an implicit conversion.
- **Missing-path behavior** — an *absent* field (a known field this request did not populate) feeds each operator's own absence rule (`no_match` for equality/ordering operators, `no_match` for `exists`, `match` for `not_exists`); an *unknown* path (one the request model does not declare, or one that reaches past a scalar leaf) always produces `error`, independent of the named operator.
- **Type-mismatch behavior** — a family mismatch is `error`, never a silent `no_match` standing in for "could not be compared."
- **Unsupported-operator behavior** — an operator name absent from `SUPPORTED_OPERATORS` always evaluates to `error`; `PolicyCondition.operator` remains structurally open (not rejected at bundle-construction time) but is never dispatched to unreviewed third-party behavior.
- **Deterministic condition ordering** — every condition in a rule's `conditions` is evaluated exactly once, in authored order, with no short-circuiting.

This roadmap item is therefore **Satisfied**, not the "deferred, structural match-only" fallback Section 16 authorized in advance as an acceptable partial release — the stronger, complete condition-evaluation path was actually implemented and merged.

### Canonical scenarios

All five canonical scenarios (`allow-basic`, `deny-precedence`, `default-deny`, `not-applicable`, `invalid-policy-bundle`) are exercised through the real `OperationAwareEnforcementPoint.evaluate()` path in `tests/operation_aware/test_canonical_vectors.py`, using real typed requests and bundles loaded from the active vendored `basis-schemas` `v0.2.2` snapshot — never a hand-typed expected value, never a test double for the engine, bundle, or any assembler. This review re-ran the suite directly: **16 passed** (each scenario asserted twice — reference-only and embedded-trace response forms). Equality is asserted for exactly three kernel-owned artifact types per scenario: `OperationAwareDecisionResponse`, `EvaluationTrace`, and `AuditEvidence`. `GatewayAuditEvent` is vendored as part of the complete cross-repository fixture family (`expected-gateway-audit-event.yaml` exists in every scenario directory) but is never loaded, constructed, or asserted against by this suite — confirmed by inspection of `tests/operation_aware/test_canonical_vectors.py`'s own scope documentation and by the repository-wide absence of any `GatewayAuditEvent` type to assert against.

### Invalid policy protection

A `PolicyBundle` that fails structural construction (Pydantic validation) or semantic validation (`validate_policy_bundle` — duplicate `rule_id` across a bundle, duplicate `condition_id` within a rule) never reaches applicability determination, selector matching, or aggregation. This is enforced structurally (a bundle that fails Pydantic construction cannot exist as a `PolicyBundle` instance at all) and semantically (`OperationAwareEvaluationEngine.evaluate()`'s stage 2 catches `SemanticPolicyValidationError` and short-circuits to a failed `EvaluationTrace` with `failure_reason=policy_validation_failure`, before stages 3–7 ever run). The canonical `invalid-policy-bundle` scenario is one of the 16 passing canonical-vector assertions. `tests/operation_aware/test_policy_validation.py` and `test_policy_bundle.py` cover the structural and semantic paths directly.

### DENY precedence

`aggregate_policy_outcome` checks deny-dominance before allow-dominance: if any evaluated rule has `result=matched` and `effect=deny`, the outcome is `deny` with `reason_code=deny_rule_matched`, independent of how many matched-allow rules are also present. Matched-but-non-decisive evidence (a matched `allow` rule that lost to a matched `deny`) remains visible in `EvaluationTrace.rule_evidence` — confirmed against `docs/operation-aware-evaluation-semantics.md` Section 5 and Section 8, and against the passing `deny-precedence` canonical scenario and `tests/operation_aware/test_policy_aggregation.py`.

### Default deny and NOT_APPLICABLE

Both remain distinct, governed outcomes under the current implementation. Default deny (`no_allow_rule_matched`, an applicable bundle with no matched deny and no matched allow, including zero evaluated rules) is textually and enum-wise distinct from explicit deny precedence (`deny_rule_matched`) and from `not_applicable` (`no_applicable_bundle`, produced when a bundle's declared scope does not cover the request at all). All three are exercised by their own canonical scenarios (`default-deny`, `deny-precedence`, `not-applicable`) and pass.

### Trace and evidence provenance

Confirmed against `docs/operation-aware-evaluation-semantics.md` Section 8 and the merged `assemble_rule_evidence` implementation:

- Matched rationale (`reason_code`/`explanation`) is preserved verbatim only for `rule_result=matched`.
- `not_matched`, `skipped`, and `error` results omit rationale (`null`/`null`) — a rule's authored success/deny rationale is never reused for an errored or non-matching result.
- Top-level `EvaluationTrace.explanation`/`OperationAwareDecisionResponse.explanation` remain `null` whenever no governed stage supplies one; assembly never synthesizes prose.
- `bundle_id`/`bundle_version` remain present whenever a trustworthy typed `PolicyBundle` exists, including the `not-applicable` and semantic-validation-failure paths, and are omitted only on the unexpected-internal-failure path where no trustworthy trace exists at all.
- `AuditEvidence.matched_rule_ids` is derived deterministically — every `rule_evidence` entry with `rule_result=matched`, in trace order — never inferred from `outcome` alone.

### Response, trace, and audit agreement

`OperationAwareDecisionResponse` enforces a narrow, deliberately-scoped agreement matrix on its own model validators when a trace is embedded: `request_id` must match; `correlation_id` must agree when both are non-null; `failure_reason` must agree; `reason_code` must agree when both are non-null. `evaluation_status`, `outcome`, `bundle_id`/`bundle_version`, and `trace_id` agreement are true by construction (response assembly copies these fields directly from the trace) rather than independently re-validated. Reference-only (`trace_id` set, `evaluation_trace=None`) versus embedded (`evaluation_trace` populated) trace presentation is controlled by the caller's `embed_evaluation_trace` argument, defaulting to `False`, never inferred. `tests/operation_aware/test_artifact_agreement.py` and `test_operation_aware_decision_response.py` cover this directly, and both canonical-vector response forms (reference-only and embedded) pass.

### Enforcement boundary

`OperationAwareEnforcementPoint` (`src/basis_core/enforcement/operation_aware.py`) is a separate class from the v0.1 `EnforcementPoint` — it does not modify, subclass, or share implementation with it, per ADR-0006 Decision 1. It is fail-closed: `evaluate()` never raises; every unexpected exception is caught and converted to `internal_evaluation_error`/`disposition=deny`. Disposition mapping is a closed two-value vocabulary (`allow`/`deny`), distinct from the three-value kernel outcome — `allow` only when evaluation completed and `response.outcome=allow`; `deny` for every other case (explicit deny, default deny, `not_applicable`, any governed failure reason, or an unexpected internal failure). No `AuditEvidence` persistence occurs anywhere in this path (no writer, no storage backend, no `write`/`save`/`persist` method), and no `GatewayAuditEvent` is constructed. The v0.1 `EnforcementPoint` is untouched by this surface — `tests/test_enforcement_point.py` passes unmodified alongside `tests/operation_aware/test_operation_aware_enforcement_point.py`.

## 6. Security and Boundary Review

Assessed against the applicable `docs/kernel-constitution.md` invariants, using evidence available in this repository — not an independent security audit.

- **Deterministic evaluation** — no clock, UUID, or random-value access anywhere in `policy/operation_aware/` or `evaluation/operation_aware/`, confirmed by the modules' own docstrings and by `docs/operation-aware-evaluation-semantics.md` Section 7's determinism inventory; `trace_id`, `evidence_id`, and `recorded_at` are caller-supplied, never generated.
- **Fail-closed enforcement** — `OperationAwareEnforcementPoint.evaluate()` never raises; every non-`completed`-`allow` case maps to `disposition=deny` (confirmed by `tests/operation_aware/test_operation_aware_enforcement_point.py` and by the merged `_derive_disposition()` implementation).
- **Separation from authentication** — no token verification, OIDC discovery, or identity-provider call anywhere in the operation-aware surface; `identity_source`/`identity_evidence_reference` are opaque, caller-supplied labels/references, never verified by the kernel.
- **Separation from protocol communication** — `protocol_context` is evidence-only, never parsed; no BACnet/Modbus/MQTT/OPC-UA/DNP3/IEC-61850/KNX/Niagara library or protocol-specific logic appears anywhere in `src/basis_core/` (confirmed by the import-boundary static scan).
- **No network dependency** — confirmed by the same static scan and by every operation-aware module's own "no I/O" docstring claims; this review did not independently instrument the code for runtime network calls beyond what the static scan and existing tests already assert.
- **No persistence** — `AuditEvidence` has no writer, storage backend, or persistence method of any kind; confirmed by direct inspection of `src/basis_core/audit/operation_aware/audit_evidence.py`.
- **No database or cloud SDK coupling** — confirmed by the import-boundary static scan (no SQLAlchemy, no cloud SDK imports anywhere in `src/`).
- **No gateway event production** — `GatewayAuditEvent` does not exist as a type anywhere in `src/basis_core/`, confirmed by repository-wide search (Section 2, "Typed operation-aware representations").
- **Bounded evidence references** — `IdentityEvidenceReference`/`AdapterEvidenceReference` are structural references (algorithm label + digest, redaction classification) with `extra="forbid"`; neither model has a field capable of holding a raw token, password, or complete claim set — confirmed by direct inspection of `src/basis_core/domain/evidence.py`.
- **Absence of raw credentials and raw protocol payload fields** — confirmed by the same inspection; no field on any operation-aware model accepts an unbounded raw payload.
- **No runtime dependency on `basis-schemas`** — `pyproject.toml`'s `dependencies` list contains only `pydantic>=2.0`; `basis-schemas` does not appear in `dependencies` or `[project.optional-dependencies].dev`, confirmed directly.

**Limits of this review, stated explicitly**: this is not a penetration test; it is not formal verification of the evaluation algorithm; it is not a performance benchmark or load test; and it is not a third-party security assessment. It is a documentation-and-test-evidence-based review performed by inspecting the merged source, the merged test suite, and the governance documents, and by re-running the existing validation suite. It does not independently prove the absence of every conceivable side channel or timing behavior.

## 8. Known Limitations and Explicit Deferrals

| Limitation | Current behavior | Why it does not block v0.2.0 | Owner / future process |
|---|---|---|---|
| Exact-match-only bundle scope | `PolicyBundleScope` applicability uses exact equality/membership only; no wildcard, hierarchical (site→building→zone→area), or prefix matching. | Explicitly documented in `docs/operation-aware-model.md` Section 4 as "a conservative first implementation... not a permanent ceiling"; none of the five canonical scenarios require broader matching. | A future, separately-reviewed broadening decision, per `docs/breaking-change-discipline.md`'s classification of this exact concern. |
| No policy-version negotiation | `OperationAwareDecisionRequest.expected_policy_version` is carried through as data; the evaluator implements no comparison or negotiation against it. | Documented non-goal (`docs/operation-aware-evaluation-semantics.md` Section 13); no canonical scenario or Section 16 item requires it. | Not currently owned by any named future PR; a future architecture decision if negotiation becomes necessary. |
| No `AuditEvidence` persistence / no `GatewayAuditEvent` | `basis-core` produces `AuditEvidence` but has no writer, storage backend, or `GatewayAuditEvent` type. | Deliberate kernel-boundary decision (ADR-0003 §14, ADR-0006 Decision 11): persistence and gateway-fact composition are `basis-gateway`'s responsibility, not the kernel's. | `basis-gateway`, per the "basis-core decides, basis-gateway enforces and records enforcement facts" boundary. |
| No performance SLA or large-bundle benchmark | No load or scale testing has been performed as part of this roadmap or this review. | Out of scope for this review and for `basis-core`'s own Definition of Done, which names no performance criterion. | Not currently owned; would require a separate benchmarking effort if a consumer surfaces a need. |
| No operation-aware executable extension point | The operation-aware policy family (`PolicyBundle` and nested shapes) is structured data; no `evaluate()`-style callback exists. | Deliberate architectural position (`docs/extension-contracts.md`'s "Operation-aware policy is structured data" section) — determinism, bounded trace/evidence, and canonical conformance all depend on centrally-governed semantics. | A future ADR in `basis-architecture` if a demonstrated need arises; not authorized informally. |
| No external authentication / no protocol communication | The kernel (including the operation-aware surface) does not verify tokens, call identity providers, or communicate with any field protocol. | Constitutional (`docs/kernel-constitution.md` Invariants 2–4), unchanged by v0.2.0 and confirmed by the import-boundary and security review above. | `basis-identity`, `basis-gateway`, `basis-adapters`, per the existing ecosystem division. |
| No topology discovery | Location/device/protocol context is caller-supplied, already-normalized data; the kernel performs no discovery or inference. | Documented non-goal (`docs/operation-aware-evaluation-semantics.md` Section 13). | Not owned by any component today; out of scope for the kernel by design. |
| Internal evaluation APIs remain unsupported | `OperationAwareEvaluationEngine` and every applicability/selector/condition/aggregation/assembly function are internal, reachable only by direct submodule import, no compatibility guarantee. | Deliberate, documented in `docs/public-api.md`'s "Internal — not exported" list and `docs/extension-contracts.md`'s "Internal evaluation machinery is not an extension contract" section. | A future, separately-scoped public-integration decision if direct evaluation-engine access is ever warranted. |
| No package-level release bump yet | `pyproject.toml`/`__init__.py` remain `0.1.0`. | Deliberate — PR 44 is the sole roadmap PR authorized to change this. | PR 44. |

None of the above is a correctness defect being relabeled as a limitation. Each is either an explicit, documented scope decision already recorded in the repository's own governance documents, or a boundary the kernel constitution assigns to a different component by design.
